# 分布式事务

## 基础

分布式事务指在跨数据源或跨服务的分布式系统中，保证业务原子性的机制。单机事务满足 ACID 原则，但分布式环境下难以直接满足。

## 核心

### 分布式事务问题

跨库跨服务的场景（如订单创建+库存扣减+账户扣款）中，每个局部事务满足 ACID，但整体业务需要原子性保证。

### 解决方案

**Seata 架构**：
- **TC（Transaction Coordinator）**：事务协调者，维护全局和分支事务状态
- **TM（Transaction Manager）**：事务管理器，定义全局事务范围
- **RM（Resource Manager）**：资源管理器，管理分支事务资源

### 四种模式

**XA 模式**（强一致）：
- 基于两阶段提交（2PC）
- 一阶段不提交事务，锁定资源；二阶段提交或回滚
- 优点：强一致、实现简单、无代码侵入
- 缺点：锁定资源时间长、性能差、依赖数据库

**AT 模式**（最终一致，Seata 默认）：
- 一阶段直接提交，记录 undo log 快照
- 二阶段删除快照或根据快照恢复
- 优点：一阶段提交性能好、无代码侵入、框架自动处理
- 缺点：软状态最终一致、快照影响性能

**TCC 模式**（最终一致）：
- Try：资源检测和预留
- Confirm：完成业务操作
- Cancel：释放预留资源
- 优点：一阶段提交、性能好、可用于非事务型数据库
- 缺点：代码侵入、需要处理空回滚和业务悬挂问题、需保证幂等

**SAGA 模式**（最终一致）：
- 长事务解决方案，各参与者正向执行，失败则逆向回滚
- 优点：异步调用、吞吐高、一阶段提交无锁
- 缺点：软状态、无事务隔离、有脏写

### 空回滚与业务悬挂

- **空回滚**：try 未执行时先执行了 cancel，需判断 try 是否已执行
- **业务悬挂**：try 在 cancel 后执行，永远无法 confirm/cancel，需在 try 时判断 cancel 是否已执行
