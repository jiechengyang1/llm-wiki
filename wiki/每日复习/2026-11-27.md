# 每日知识点 · 2026-11-27（第 5/76 天）

## 今日新知：[[分布式锁]]

### 要点速览

- **为什么需要**：分布式系统多个进程并发访问共享资源，需要分布式锁保证互斥，防止数据不一致
- **五大特性**：互斥性 · 可重入 · 死锁避免（崩溃后能自动释放）· 公平性 · 性能
- **三种实现**：数据库（乐观锁 / 唯一索引，性能低）、Redis（SETNX+EXPIRE，高性能）、Zookeeper（临时有序节点 + Watch，可靠性高）
- **Redis 加锁必须原子**：`SETNX` 和 `EXPIRE` 分开执行，一旦中间崩溃锁就永不过期 → 死锁；用 Lua 脚本或 `SET key value NX EX` 一条命令完成
- **Redisson 三大能力**：看门狗自动续期（业务没跑完锁不过期）、可重入（hash 结构存重入次数）、公平锁（有序队列）
- **三大经典问题**：① 锁过期业务未完成 → 看门狗续期；② 主从切换锁丢失 → RedLock 多数派算法；③ 误删他人锁 → value 存唯一标识 + Lua 校验后删除
- **Redis vs ZK**：Redis 性能高但可靠性中（主从切换丢锁）；ZK 可靠性高、天然支持公平（临时有序节点），性能中等
- **选型建议**：优先 Redisson 成熟方案；强一致性场景选 Zookeeper；性能极致要求选 Redis

### 自测三题（先自己答，再展开对答案）

1. Redis 实现分布式锁时，为什么 SETNX 和 EXPIRE 必须原子执行？不原子会出什么问题？
2. Redisson 的看门狗机制解决什么问题？它是怎么工作的？
3. 如何避免「误删他人的锁」？value 里应该存什么？

> [!success]- 参考答案
> 1. 分开执行时，SETNX 成功后客户端崩溃、EXPIRE 未执行 → 锁永不过期 → 其他客户端永远拿不到锁（死锁）。解决：Lua 脚本原子执行，或 `SET key value NX EX seconds` 单命令。
> 2. 解决「业务执行时间 > 锁过期时间」导致锁提前释放、他人闯入的问题。看门狗在持锁期间后台定时续期（默认锁 30s、每 10s 检查续一次），业务执行完/客户端崩溃才停止续期。
> 3. value 存 UUID 或「客户端ID:线程ID」等唯一标识；解锁时用 Lua 脚本先 get 比对 value 再 del，保证「校验+删除」原子性，只删自己加的锁。

## 昨日回顾：[[Java集合]]

- **List 对比**：ArrayList（数组，随机访问/尾插）、LinkedList（双向链表，频繁插删）、CopyOnWriteArrayList（读多写少的并发场景）
- **Map 选型**：HashMap 高性能 · LinkedHashMap 保插入序 · TreeMap 自然排序 · **ConcurrentHashMap 高并发首选**
- **fail-fast**：迭代时校验 modCount，被结构性修改就抛 `ConcurrentModificationException`；避免方式：迭代器自身 remove() 或并发集合
